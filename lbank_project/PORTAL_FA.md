# پنل مرکزی کاربران و اتصال حساب شخصی صرافی

## آنچه اجرا می‌شود

این سرویس مستقل از داشبورد تک‌مشتری است. هر مشتری با نام کاربری و رمز خودش
وارد می‌شود، صرافی خودش را انتخاب و کلیدهای آن را ثبت/حذف می‌کند و فقط موجودی و اجرای اختصاصی
متصل به حساب خودش را می‌بیند. انتخاب مالک داده از session سمت سرور انجام می‌شود؛
هیچ API کاربری شناسه مالک، مسیر runtime یا آدرس دلخواه صرافی قبول نمی‌کند.
اسکریپت ربات قبلی، سرمایه آزمایشی و استراتژی‌های آن تغییر نمی‌کنند.

**این نسخه پایلوت است؛ آمادگی سرویس‌دهی به ۱۰ هزار حساب فعال تأیید نشده است.**
پایگاه داده SQLite برای تست و پایلوت است، نه استقرار توزیع‌شدهٔ نهایی.
پشتیبانی PostgreSQL، صف پایدار و worker مستقل اکنون اضافه شده‌اند؛ راه‌اندازی
و نتایج ظرفیت را در [CENTRAL_SERVICE_FA.md](CENTRAL_SERVICE_FA.md) بخوانید.

## حدود اتصال صرافی و ربات

پوشش فعلی ۹ صرافی، credentialها و ۷ مسیر خواندن Futures در
[MULTI_EXCHANGE_FA.md](MULTI_EXCHANGE_FA.md) آمده است. توضیح زیر دربارهٔ محدودیت
خاص LBank است؛ بقیهٔ صرافی‌ها از آداپتورهای جدا استفاده می‌کنند.

ثبت کلید، اتصال تأییدشده و شروع ربات سه وضعیت متفاوت‌اند.
آداپتور LBank فقط endpoint حساب Spot را می‌خواند و نتیجه را به موجودی نرمال‌شده
تبدیل می‌کند. حساب Spot به حساب Futures تبدیل یا به جای آن نمایش داده نمی‌شود.
کلید Futures قابل ثبت رمزگذاری‌شده است، ولی بررسی آن وضعیت
`futures_not_validated` می‌دهد؛ موجودی و پوزیشن Futures هنوز خوانده نمی‌شوند.
هیچ سفارش، انتقال، برداشت یا روشن‌کردن ربات واقعی در این پنل وجود ندارد.
اتصال واقعی با کلید مشتری در این محیط تست نشده؛ تست آداپتور با پاسخ ساختگی بود.

در پنل، وضعیت و پوزیشن/معاملات اخیر سه ربات فقط از runtime آزمایشی‌ای خوانده
می‌شود که مدیر به همان کاربر متصل کرده باشد. اگر runtime متصل نباشد، پنل
«راه‌اندازی نشده» نشان می‌دهد. برای موج‌سوار و ققنوس heartbeat اختصاصی وجود
ندارد؛ وضعیت زنده آن‌ها نامشخص نمایش داده می‌شود، نه فعال ساختگی.
خاموش‌کردن حساب کاربری پنل یا حذف اتصال، فرمان توقف پردازش ربات نیست.

## اجرای محلی پایلوت

در پوشه lbank_project:

```bash
python -m pip install -r requirements.txt
python portal_admin.py init
python portal_admin.py create-user alice
python portal_admin.py create-user bob
export PORTAL_KEY_FILE="$PWD/issuer-keys/portal.key"
export PORTAL_ORIGIN=http://127.0.0.1:8080
export PORTAL_ALLOW_LOCAL_HTTP=1
python portal_server.py
```

در یک ترمینال دیگر با همان PORTAL_KEY_FILE و تنظیمات پایگاه داده:

```bash
python portal_worker.py
```

دکمهٔ بررسی اتصال پاسخ ۲۰۲ می‌دهد؛ خواندن صرافی در worker انجام می‌شود و پنل
تا آماده‌شدن نتیجه، وضعیت را با درخواست GET تازه می‌کند. بدون worker، کار در صف می‌ماند.

رمز هنگام ایجاد کاربر با getpass وارد می‌شود؛ در command history یا آرگومان
پردازش ثبت نمی‌شود. طول رمز ۱۲ تا ۱۲۸ کاراکتر است. سایت در
http://127.0.0.1:8080 باز می‌شود. کلیدهای صرافی را فقط در فرم پنل وارد کنید؛
در چت، فایل Git یا دستور خط فرمان نگذارید. برای مشاهده حساب، API فقط‌خواندنی
و بدون مجوز برداشت بسازید و مطابق مستندات LBank محدودیت IP را تنظیم کنید.

در PowerShell، به جای export از متغیرهای زیر استفاده کنید:

```powershell
$env:PORTAL_KEY_FILE = "$PWD/issuer-keys/portal.key"
$env:PORTAL_ORIGIN = "http://127.0.0.1:8080"
$env:PORTAL_ALLOW_LOCAL_HTTP = "1"
python portal_server.py
```

برای Docker بعد از init و ایجاد کاربران روی میزبان:

```bash
export PORTAL_ALLOW_LOCAL_HTTP=1
docker compose -f portal-compose.yml up -d --build
```

Docker در محیط توسعه حاضر نبود؛ این فایل هنوز با موتور Docker اعتبارسنجی نشده است.
Compose پیش‌فرض هیچ runtime مشتری را mount نمی‌کند. برای نمایش ربات‌ها در
کانتینر، مدیر باید runtime موردنظر را در مسیر ثابت read-only mount کند و همان
مسیر داخل کانتینر را با فرمان bind-runtime ثبت کند. مسیر میزبان و کانتینر یکی نیستند.

## اتصال اجرای آزمایشی اختصاصی

پس از ساخت و شروع نصب مستقل مشتری با customer_manager و customer_entrypoint،
فایل customer_identity.json در runtime ایجاد می‌شود. مدیر می‌تواند آن را متصل کند:

```bash
python portal_admin.py bind-runtime alice customers/alice/runtime
```

شناسهٔ ثبت‌شده runtime باید با نام کاربری یکی باشد و در هر بار نمایش دوباره
بررسی می‌شود. یک runtime به دو کاربر متصل نمی‌شود. عملیات bind فقط فرمان مدیریتی است؛
از HTTP در دسترس نیست. برای عوض‌کردن رمز یا قطع دسترسی پنل:

```bash
python portal_admin.py reset-password alice
python portal_admin.py disable-user alice
```

عوض‌کردن رمز، نشست‌های قبلی را باطل می‌کند. disable-user ورودهای قبلی و جدید
را می‌بندد؛ ربات و مدیریت پوزیشن‌های آن را متوقف نمی‌کند.

## امنیت پیاده‌سازی‌شده

- رمزها با scrypt و salt مستقل هش می‌شوند؛ کلیدهای API با Fernet ذخیره می‌شوند.
- مالک داخل محتوای رمزگذاری‌شده نیز بررسی می‌شود تا جابه‌جایی ciphertext بین کاربران پذیرفته نشود.
- master key خارج از دیتابیس و Git نگه داشته می‌شود؛ از آن جداگانه پشتیبان امن بگیرید.
- cookie نشست HttpOnly/SameSite=Strict است؛ استقرار HTTPS، Secure cookie اجباری دارد.
- CSRF token و Origin بررسی می‌شوند؛ CORS باز، ثبت‌نام عمومی و مسیر HTTP مدیریت وجود ندارد.
- تلاش ورود در دیتابیس محدود می‌شود: ۱۰ درخواست در ۶۰ ثانیه برای هر client، مشترک بین پردازش‌ها.
- هر حساب فقط یک کار بررسی در صف/اجرا دارد؛ پس از بررسی، درخواست جدید تا ۳۰ ثانیه محدود می‌شود.
- نرخ شروع بررسی‌ها برای هر صرافی بین workerها مشترک است؛ پیش‌فرض حداکثر ۴ کار در ثانیه برای هر صرافی، نه تضمین محدودیت اعلامی آن.
- پاسخ دیررس اتصال قبلی، پس از تغییر/حذف کلید، نمی‌تواند کش حساب را دوباره زنده کند.
- خطای SDK و ورودی نامعتبر، کلید/Secret را در پاسخ یا log بازتاب نمی‌دهند.
- کلید در مرورگر persist نمی‌شود و پس از ثبت پاک می‌شود؛ داده‌های صفحه no-store هستند.

کلید master امکان رمزگشایی همهٔ کلیدهای مشتریان را دارد؛ این نسخه KMS/HSM نیست.
برای انتشار اینترنتی، TLS روی reverse proxy، سقف اندازه/نرخ درخواست در لبه،
حفاظت میزبان، کنترل دسترسی مدیر و پشتیبان سازگار با SQLite WAL لازم است.
PORTAL_ORIGIN باید آدرس دقیق HTTPS سایت باشد و PORTAL_ALLOW_LOCAL_HTTP خاموش بماند.
Uvicorn پیش‌فرض به proxy headers اعتماد نمی‌کند؛ برای پراکسی شناخته‌شده، فقط
IP یا CIDR دقیق آن را در PORTAL_TRUSTED_PROXY_IPS ثبت کنید. wildcard پذیرفته
نمی‌شود. تنظیم درست این مقدار و rate limit لبه باید پیش از انتشار انجام شود.

## مسیر لازم برای ۱۰ هزار مشتری

هدف نهایی حساب شخصی هر کاربر روی سرویس مرکزی است، بدون دریافت سپردهٔ مشتری.
این پایلوت فقط مرز مالکیت، پنل و ذخیرهٔ اتصال را فراهم می‌کند. پیش از عرضه عمومی:

1. PostgreSQL با connection pool و انتقال داده پیاده شد؛ تأیید استقرار native،
   پشتیبان‌گیری و سیاست نگهداری audit هنوز لازم است.
2. worker و صف جدا برای خواندن حساب پیاده شد؛ API منتظر صرافی نمی‌ماند.
   این worker سفارش اجرا نمی‌کند؛ سقف مناسب LBank باید برای سرور تأیید شود.
3. دریافت یک‌بارهٔ دادهٔ بازار و محاسبهٔ سیگنال مشترک؛ سرمایه، ریسک، پوزیشن و
   ترتیب اجرای سفارش کاملاً اختصاصی هر حساب. مشتری نباید فرایند Docker جدا لازم داشته باشد.
4. دریافت قرارداد دقیق API خصوصی Futures و تأیید با حساب کنترل‌شده: موجودی،
   پوزیشن، سفارش باز، وضعیت fill، client order ID و حفاظت stop پس از قطعی.
5. افزودن executor واقعی با reconcile پس از restart، idempotency، جلوگیری از
   دوباره‌فرستادن سفارش پس از timeout و ادامهٔ مدیریت خروج هنگام انقضای اشتراک.
6. ثبت‌نام/تأیید هویت حساب کاربری، MFA، پرداخت و اشتراک، reset-password امن،
   KMS و چرخش کلید، نظارت و پشتیبان قابل بازیابی.
7. تست ۱۰ هزار حساب فعال با پاسخ صرافی شبیه‌سازی‌شده و محدودیت نرخ واقعی:
   p95 خواندن پنل زیر ۵۰۰ms به‌عنوان هدف اولیه، صفر نشت بین مشتریان، صفر سفارش
   تکراری، بازیابی worker بدون از دست‌رفتن مالکیت پوزیشن. این اعداد هدف پذیرش‌اند، نتیجهٔ تست فعلی نیستند.

```bash
python -m pip install -r requirements-dev.txt

python -m pytest tests/test_portal_queue.py -q
node --check portal.js
node tests/test_portal_ui.cjs
```

تست‌ها شامل جداسازی دو حساب، رد انتخاب مالک دیگر، vault مالک‌محور، ابطال نشست،
CSRF/Origin/Host، محدودیت ورود مشترک، پاک‌شدن کش پس از تعویض کلید، عدم بازتاب
Secret در خطا و خواندن مستقل runtime هستند. این‌ها تست سودآوری، صرافی واقعی
یا ظرفیت ۱۰ هزار مشتری نیستند.

در این محیط تأیید نشده‌اند.
