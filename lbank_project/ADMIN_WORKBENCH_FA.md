# کارتابل مدیر سامانه

مسیر پنل مدیریت: **`/admin/`**. رابط با Next.js و TypeScript ساخته شده، فارسی و
واکنش‌گراست و از همان نشست و کوکی HttpOnly پنل مشتری استفاده می‌کند.
تمام مسیرهای `/api/admin/*` نقش مدیر را سمت سرور بررسی می‌کنند؛ پنهان‌شدن یک
دکمه، کنترل دسترسی محسوب نمی‌شود. نقش از اطلاعات نشستِ بازیابی‌شده از DB می‌آید،
نه پارامتر مرورگر. تغییر نقش، همهٔ نشست‌های قبلی همان کاربر را می‌بندد.

## ساخت اولین مدیر

ابتدا حساب را از صفحهٔ ثبت‌نام بسازید یا از دستور create-user قبلی استفاده کنید.
سپس اپراتور دارای دسترسی سرور، از پوشهٔ `lbank_project` و با همان DB و کلید
رمزگذاری پنل، نقش را تنظیم کند:

```bash
python portal_admin.py set-admin USERNAME
```

کاربر دوباره وارد شود و `/admin/` را باز کند. مدیر در پنل مشتری نیز لینک
«کارتابل مدیریت» را می‌بیند. هیچ حساب، رمز پیش‌فرض، ارتقای خودکار اولین کاربر
یا مسیر عمومیِ مدیرکردن حساب وجود ندارد. حذف نقش از مسیر سرور:

```bash
python portal_admin.py set-admin USERNAME --remove
```

ثبت‌نام همچنان فقط حساب مشتری می‌سازد. تغییر نقش و تعلیق حساب‌های مدیر از پنل
وب پشتیبانی نمی‌شود تا مدیر نتواند دسترسی خودش را ناخواسته ببندد؛ اپراتور سرور
آن‌ها را مدیریت می‌کند.

## بخش‌های کارتابل

- **نمای کلی:** تعداد کاربران، درخواست‌های در انتظار، کل لایسنس‌های صادرشده،
  صف صدور و تعداد موارد ناموفق. «صادرشده» به معنی معتبربودن فعلی همهٔ دوره‌ها نیست.
  آخرین فعالیت سرویس صدور نمایش داده می‌شود؛ نبود فعالیت، فعال فرض نمی‌شود.
- **کاربران:** جست‌وجو و صفحه‌بندی، مشاهدهٔ نقش و وضعیت، وجود اتصال و runtime،
  تعلیق و فعال‌سازی مشتری. تعلیق، نشست‌های مشتری را فوراً حذف می‌کند. رمز،
  هش رمز، API Key، Secret و مسیر runtime در فهرست مدیر برگردانده نمی‌شوند.
- **درخواست‌ها:** فیلتر وضعیت، بررسی مبلغ و محصول، رد با دلیل داخلی، تأیید
  بررسی رسید و اطلاعات حساب و ارسال به صف صدور، مشاهدهٔ صف/خطا و تلاش مجدد.
- **قیمت و فروش:** ویرایش ۲۱ قیمت دلاری هر محصول، ذخیرهٔ پیش‌نویس و بستن فروش،
  تأیید جداگانهٔ نهایی‌بودن قیمت‌ها و بازکردن فروش، بستن فروش هر محصول به‌طور مستقل.
- **سوابق عملیات:** نام مدیر یا اپراتور سرور، زمان تهران، نوع عملیات و شناسهٔ موضوع.
  تغییر کاربر، تعرفه، فروش، رد/تأیید سفارش و نتیجهٔ صدور ثبت می‌شوند.

فهرست‌ها محدود و صفحه‌بندی شده‌اند. تمام عملیات تغییردهندهٔ وب، کنترل مبدأ و
CSRF دارند. ویرایش هم‌زمان تعرفه با نسخهٔ مورد انتظار کنترل می‌شود؛ تب قدیمی
نمی‌تواند بی‌خبر قیمت تازه را بازنویسی کند.

**فروش هر دو محصول همچنان طبق تصمیم مالک بسته می‌ماند.** افزودن کارتابل،
بیلد، مهاجرت یا ذخیرهٔ پیش‌نویس فروش را باز نمی‌کند. بازکردن فروش نیاز به
قیمت کامل ذخیره‌شده و اقدام صریح مدیر دارد. این تغییر کد هیچ فروش یا حساب
مدیریتی در محیط فعلی فعال نکرده است.

## سرویس صدور جدا از وب

کلید خصوصی صادرکننده به مرورگر آپلود نمی‌شود و در کانتینر عمومی وب قرار نمی‌گیرد.
تأیید در کارتابل ابتدا یک درخواست پایدار با وضعیت queued می‌سازد. تا امضای موفق،
لایسنس فعال نمی‌شود و سفارش pending می‌ماند.

برای پردازش صف، با دسترسی مدیریتی روی سرور یا کانتینر جدا، همان DB و
PORTAL_KEY_FILE پنل را تنظیم کنید و از کلید صادرکنندهٔ متناظر با نصب مشتریان
استفاده کنید:

```bash
python portal_issuer.py --private-key issuer-keys/license.private.pem
```

پردازش یک نوبت و خروج:

```bash
python portal_issuer.py --private-key issuer-keys/license.private.pem --once
```

`Dockerfile.issuer` برای تصویر مستقل سرویس صدور آماده شده است. در استقرار آن،
فقط این سرویس باید secret کلید خصوصی را در `/run/secrets/license_private`
دریافت کند. همان کلید رمزگذاری پنل و اتصال DB نیز لازم‌اند. در SQLite پوشهٔ
runtime/portal مشترک و در PostgreSQL همان تنظیم اتصال استفاده شود.
این سرویس عمداً خودکار به Compose وب اضافه نشده تا کلید خصوصی به‌اشتباه
در سرویس عمومی mount نشود. Dockerfile پنل، کد رابط مدیریت را می‌سازد ولی
کلید خصوصی یا worker صدور را به وب نمی‌دهد.

در هر صدور، قیمت جاری و وضعیت فروش، اعتبار سفارش، نقش مدیر درخواست‌دهنده،
فعال‌بودن مشتری و یکتابودن رسید دوباره بررسی می‌شوند. تغییر تعرفه یا بستن فروش
می‌تواند یک درخواست صف‌شده را ناموفق کند. خطای عمومی در کارتابل نمایش داده
می‌شود؛ متن exception یا مسیر کلید خصوصی در API قرار نمی‌گیرد.

صف از lease و token استفاده می‌کند. worker قدیمی یا lease منقضی نمی‌تواند
دوباره لایسنس صادر کند. پس از توقف غیرمنتظره، lease درخواست حداکثر سه بار قابل بازیابی است.
خطای صدور مستقیماً برای رسیدگی مدیر failed می‌شود؛ مهلت‌های سه‌بار منقضی‌شده
نیز به رسیدگی مدیر نیاز دارند. مدیر در تلاش مجدد
باید رسید و اطلاعات را دوباره وارد و بررسی را تأیید کند.

## مرز اثر اقدامات

تعلیق کاربر، دسترسی پنل را قطع می‌کند؛ پوزیشن باز را نمی‌بندد و فایل لایسنس
آفلاین نصب‌شده روی ربات را از راه دور باطل نمی‌کند. رد سفارش فقط برای درخواست
pending ممکن است و درخواست صدور آن را لغو می‌کند. لایسنس صادرشده با رد سفارش
حذف نمی‌شود. بستن فروش، اشتراک پرداخت‌شده را باطل نمی‌کند.

پرداخت همچنان دستی بررسی می‌شود؛ «تأیید» به معنی مشاهده و تأیید واقعی رسید
توسط مدیر است، نه استعلام بانکی خودکار. اشتراک autotrade به شناسه و اکوییتی
تأییدشدهٔ حساب نیاز دارد. پس از صدور، فایل آن باید روی نصب مشتری اعمال شود.
اشتراک signals از پنل تحویل می‌شود. اجرای سفارش واقعی صرافی با افزودن این
کارتابل فعال نمی‌شود و موتور فعلی همچنان paper است.

## بیلد و مهاجرت

```bash
npm --prefix frontend ci
npm --prefix frontend run build
```

پنل معمول را با تنظیمات قبلی اجرا کنید. schema=6 خودکار ستون نقش و جدول‌های
صف/سوابق را اضافه می‌کند؛ کاربران قبلی customer باقی می‌مانند. پیش از ارتقای
سرویس موجود، از DB و کلید رمزگذاری جداگانه پشتیبان بگیرید. مهاجرت آفلاین
نقش‌ها و سوابق را حفظ و leaseهای در حال اجرا را به صف قابل پردازش برمی‌گرداند.

## تست

```bash
PYTHONPATH=. python -m pytest tests/test_admin_workbench.py tests/test_admin_browser.py -q
```

تست مرورگر به Chromium و Playwright نیاز دارد. DB، کاربران، قیمت، رسید و
کلیدهای تست موقتی‌اند؛ هیچ حساب واقعی یا فروش تولیدی فعال نمی‌شود. تست‌ها
شامل جلوگیری از دسترسی مشتری، CSRF، ابطال نشست، تأیید جداگانهٔ قیمت، صف صدور،
رد/تلاش مجدد، تغییر نقش پیش از صدور، lease منقضی، صدور هم‌زمان، مهاجرت و
نمایش موبایل هستند.
