# اتصال هر کاربر به صرافی انتخابی خودش

پنل اکنون انتخاب صرافی و نوع حساب دارد. هر کاربر **یک اتصال فعال** مستقل دارد؛
می‌تواند آن را تغییر دهد. این قابلیت، اجرای سه ربات آزمایشی را به معاملهٔ واقعی
تبدیل نمی‌کند. چند حساب/صرافی هم‌زمان برای یک کاربر هنوز پیاده نشده است.

## پوشش نسخهٔ فعلی

| صرافی | Spot | آداپتور مشاهدهٔ Futures | محدوده |
|---|---|---|---|
| LBank | دارد | مسدود تا تأیید API خصوصی | موجودی Spot |
| Binance | دارد | دارد | USD-M؛ آداپتور binanceusdm جداست |
| Bybit | دارد | دارد | UTA یا classic؛ پوزیشن‌های خطی USDT، حداکثر ۳ صفحه |
| OKX | دارد | دارد | موجودی حساب معاملاتی مشترک؛ پوزیشن SWAP |
| Bitget | دارد | دارد | حساب classic، USDT Futures؛ UTA فعال نشده |
| Gate | دارد | دارد | قرارداد دائمی با تسویه USDT |
| KuCoin | دارد | دارد | حساب classic؛ kucoinfutures جدا از Spot |
| Kraken | دارد | دارد | حساب Kraken Futures جدا از Spot |
| Coinbase Exchange | دارد | ندارد | حساب Exchange؛ معادل همهٔ محصولات Coinbase نیست |

«دارد» یعنی مسیر SDK پیاده و با پاسخ کنترل‌شده تست شده؛ **تأیید اتصال زنده با
کلید مشتری نیست**. نسخهٔ CCXT قفل‌شده 4.5.85 است. در مجموع ۹ صرافی و ۷ مسیر
خواندن Futures وجود دارد. منظور از Futures در این پنل عمدتاً قرارداد دائمی است،
نه تضمین پوشش همهٔ قراردادهای تاریخ‌دار، معکوس، Options یا همهٔ زیرحساب‌ها.

هر صرافیِ دلخواه فقط زمانی قابل استفاده است که آداپتور و مجوز حساب لازم را
داشته باشد. فهرست قابل گسترش است؛ از ادعای پشتیبانی خودکار «تمام صرافی‌ها»
بدون بررسی endpoint و نوع حساب اجتناب شده است. صرافی خارج از فهرست با ۴۲۲
رد می‌شود و هیچ کلیدی به آدرس دلخواه کاربر ارسال نمی‌شود.

## استفاده

۱. در پنل خود وارد شوید؛ صرافی و نوع حساب را انتخاب کنید.
۲. API Key و Secret را وارد کنید. Passphrase برای OKX، Bitget، KuCoin و
Coinbase Exchange نیز لازم است و فرم آن را نشان می‌دهد. کلید فقط‌خواندنی و
بدون مجوز برداشت برای مشاهدهٔ حساب مناسب است.
۳. «ثبت کلیدهای حساب» اتصال را رمزگذاری‌شده ذخیره می‌کند؛ هنوز verified نیست.
۴. «بررسی اتصال» کار را به worker می‌دهد. بعد از دریافت موفق موجودی و، برای
Futures، پوزیشن‌ها، وضعیت verified_read_only می‌شود.

پنل موجودی صرافی و پوزیشن‌های گزارش‌شده را جدا از معاملات آزمایشی سه ربات
نشان می‌دهد. تعداد contracts الزاماً مقدار ارز پایه نیست؛ contract_size در API
نیز ارائه می‌شود. missing balance و PnL با صفر ساختگی جایگزین نمی‌شوند.
برای کیف پول یکپارچه، موجودی بین Spot و Futures مشترک است؛ balance_scope در
پنل نمایش داده می‌شود تا آن را سرمایهٔ اختصاصی همان استراتژی تلقی نکنید.
پوزیشن‌ها ممکن است محدود به نوع قرارداد/تسویه/تعداد صفحات آداپتور باشند؛
positions_complete برای Futures false است و پنل این محدودیت را نشان می‌دهد.

## مالکیت و تغییر اتصال

- کلید، Secret، Passphrase و UID رمزگذاری می‌شوند و در GET/خطای اعتبارسنجی برنمی‌گردند.
- envelope رمزگذاری‌شده به owner، exchange_id و market بسته است. تغییر metadata دیتابیس، انتقال کلید به صرافی دیگر را مجاز نمی‌کند.
- دادهٔ قدیمیِ بدون exchange_id فقط متعلق به LBank شناخته می‌شود.
- عوض‌کردن صرافی، بازار یا کلید، revision را عوض و cache/job قبلی را حذف می‌کند. پاسخ worker قدیمی رد می‌شود.
- فرم با تغییر صرافی/بازار، فیلدهای کلید را پاک می‌کند؛ آن‌ها خودکار به صرافی بعدی منتقل نمی‌شوند.
- نام صرافی از registry سرور می‌آید. URL، options دلخواه CCXT و مالک دلخواه در API پذیرفته نمی‌شوند.
- هر حساب متعلق به session خودش است؛ backend از شناسهٔ مشتری ارسالی در درخواست برای انتخاب داده استفاده نمی‌کند.

## نرخ و بازیابی

gate اکنون برای هر صرافی مستقل و بین تمام workerها مشترک است؛ Binance Spot
و Futures در bucket یک Binance هستند. شلوغی یک صرافی، صرافی دیگر را معطل
همان gate نمی‌کند. پیش‌فرض فاصلهٔ شروع کار ۰٫۲۵ ثانیه برای هر صرافی است.
این حد مربوط به **شروع کار** است، نه تعداد HTTP داخلی SDK؛ یک کار ممکن است
چند درخواست بازار/موجودی/پوزیشن داشته باشد. سقف واقعی API هر صرافی باید تأیید شود.

تنظیم اختیاری روی سرور:

```bash
export PORTAL_EXCHANGE_READ_INTERVAL=0.5
export PORTAL_EXCHANGE_READ_INTERVALS='{"binance":1.0,"bybit":0.5,"okx":1.0}'
```

مقادیر عددی باید متناهی و بین ۰٫۰۱ و ۶۰ ثانیه باشند؛ نام صرافی ناشناخته پذیرفته
نمی‌شود. PORTAL_LBANK_READ_INTERVAL قدیمی برای سازگاری به‌عنوان fallback باقی است.

خطای DB هنگام انتشار نتیجه از خطای صرافی جداست: worker نتیجهٔ موفق صرافی را
به‌علت خطای DB به failed-auth تبدیل نمی‌کند. lease برای بازیابی باقی می‌ماند.
خطای شبکه retry محدود دارد؛ خطای قابلیت/احراز هویت، بدون چاپ Secret، ثبت می‌شود.

## ارتقا و آزمون

schema نسخهٔ ۳، ستون exchange_id را با default=lbank اضافه می‌کند. کلیدهای
پایلوت قبلی حفظ می‌شوند. ابزار انتقال SQLite به PostgreSQL، پایگاه قدیمیِ بدون
این ستون را نیز با LBank منتقل می‌کند. پنل و workerهای قدیمی را قبل از ارتقا
متوقف کنید؛ source/image هر دو باید هم‌نسخه شوند.

```bash
python -m pip install -r requirements-dev.txt -r requirements-portal.txt
python -m pytest tests -q
node tests/test_portal_ui.cjs
python portal_capacity.py --users 10000 --requests 2000 --concurrency 40 --drain 1000 --mix-exchanges --mix-markets --output reports/new-multi-exchange-run.json
```

تست‌های آداپتور بدون تماس واقعی صرافی اجرا می‌شوند: مسیر جداگانهٔ Binance و
KuCoin Futures، پارامترهای نوع حساب، Passphrase، عدم انتشار info/Secret،
مالکیت دو کاربر در دو صرافی، تعویض اتصال در میانهٔ worker، gate مستقل، مهاجرت
LBank قدیمی و رد دستکاری provider/market آزموده شده‌اند. خطای انتشار DB نیز
تزریق و بازیابی آن بررسی می‌شود.

### نتایج اجرای ۲۰۲۶-۱۰-۱۳

مجموعهٔ کامل: **۳۶۱ موفق، ۲۰ skipped** (۱۰ دادهٔ پژوهشی غایب و ۱۰ تست نیازمند
URL موقت PostgreSQL). ماتریس جداگانهٔ صف SQLite/PostgreSQL-WASM: **۲۲ موفق**؛
تست UI نیز موفق بود. WASM جایگزین تأیید قفل‌ها و ظرفیت PostgreSQL native نیست.

آزمون چندصرافی با ۱۰ هزار حساب مصنوعی، ۹ صرافی و ۱۶ مسیر حساب:

| شاخص | نتیجه |
|---|---|
| worker محلی SQLite | ۱ |
| کار دریافت‌شده / موفق / ناموفق | ۱۰۰۰ / ۱۰۰۰ / صفر |
| کار باقی‌مانده در صف | ۹۰۰۰ |
| درخواست پنل / هم‌زمانی / پاسخ موفق | ۲۰۰۰ / ۴۰ / ۲۰۰۰ |
| صدک ۹۵ / ۹۹ | ۱۱۶٫۸۶ / ۱۴۰٫۵۰ میلی‌ثانیه |
| نمونهٔ دارای موجودی / مغایرت مالکیت در نمونه‌ها | ۱۹۲ / صفر |
| تماس واقعی صرافی / سفارش واقعی | صفر / صفر |

خروجی: `reports/multi_exchange_capacity_10000_v2.json`. اجرای قبلی با چهار worker
در `reports/multi_exchange_capacity_10000.json` یک کار failed داشت؛ تکرار آن پس
از اصلاح تفکیک خطا، `database is locked` را آشکار کرد. این مشکل نوشتن هم‌زمان
SQLite رفع نشده و نتیجهٔ اجرای تک-worker تأیید رفع آن نیست. اجرای محلی SQLite
باید یک worker داشته باشد؛ استقرار چند-worker برای مشتریان روی PostgreSQL
است و پیش از عرضه به آزمون native، شبکه و کلید فقط‌خواندنی واقعی نیاز دارد.
این آزمون ۱۰ هزار کار کامل یا ۱۰ هزار session هم‌زمان را پوشش نمی‌دهد.

## اضافه‌کردن صرافی دیگر

در portal_exchanges.PROFILES، route خواندن موجودی و پوزیشن، CCXT client،
credentialهای لازم، نوع کیف پول، تسویه و pagination را تعریف کنید. factory فقط
شناسهٔ بررسی‌شدهٔ SDK را می‌سازد؛ user URL قبول نمی‌کند. قبل از افزودن به فهرست،
تست مستقل مسیر Spot/Futures و تست فقط‌خواندنی حساب کنترل‌شده لازم است.

برای **معاملهٔ واقعی**، هنوز executor، تطبیق نماد/contract size، precision و
حداقل حجم، SL/TP صرافی، idempotency، reconcile و رفتار قطعی باید برای هر
صرافی جدا تکمیل شوند. اتصال فقط‌خواندنی به معنی تأیید این بخش‌ها نیست.

منبع قابلیت‌ها: کد رسمی CCXT 4.5.85 برای هر provider در بستهٔ نصب‌شده و
https://github.com/ccxt/ccxt ؛ مستندات https://docs.ccxt.com/ .
